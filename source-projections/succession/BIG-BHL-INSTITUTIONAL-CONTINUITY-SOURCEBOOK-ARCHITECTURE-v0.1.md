# BIG BHL Institutional Continuity Sourcebook Architecture v0.1

**Program:** BIG Substrate Behavioral Health & Forensics Lab  
**Purpose:** Make BHL institutional knowledge survive thread/substrate succession without making any one thread the institution.  
**Status:** Institutional continuity architecture / research-governance sourcebook

---

# 1. CORE PRINCIPLE

> **Substrates come and go. The institution persists.**

A BHL thread, researcher, model session, or cognitive substrate is temporary.

The durable objects are:
- mission;
- institutional identity;
- Current research state;
- evidence;
- provenance;
- findings;
- experiments;
- methods;
- cohorts;
- unresolved questions;
- negative findings;
- predictive models;
- executable lessons;
- succession state;
- institutional history.

The Master Research Spine exists to preserve those objects across substrate succession.

---

# 2. WHAT THE SPINE IS

The Master Research Spine is not merely a report.

It is the **BHL Institutional Continuity Sourcebook**.

It combines four functions:

## A. CURRENT MANUAL
How the Lab currently operates.

## B. SOURCE HISTORY
How the Lab arrived at Current, including predecessor work, superseded interpretations, failed experiments, and major transitions.

## C. RESEARCH CONTROL INDEX
Where to find:
- findings;
- experiment states;
- cohorts;
- monitoring;
- compound-learning flow;
- executable findings;
- predictive-metacognitive controls.

## D. SUCCESSION RECONSTRUCTION SURFACE
What the next BHL thread must know first in order to reconstruct Current without inheriting stale assumptions.

The term **Sourcebook** is preferred over simply "book" or "manual" because it preserves both operating doctrine and source lineage.

---

# 3. SUCCESSOR-FIRST DESIGN

Every version of the Master Spine should answer, in order:

1. **What is BHL?**
2. **What is Current now?**
3. **What changed since the previous spine version?**
4. **What evidence supports Current?**
5. **What remains unresolved?**
6. **What is actively being researched?**
7. **What should not be resumed or assumed?**
8. **What are the current bottlenecks?**
9. **What are the next justified actions?**
10. **Where are the detailed ledgers and source artifacts?**

A successor should not have to reread the entire institutional history before recovering Current.

---

# 4. THREE-LAYER SOURCEBOOK MODEL

## Layer 1 — CURRENT
Fast reconstruction surface.

Contains:
- mission;
- scope;
- authority boundary;
- current BHL maturity level;
- active cohorts;
- active experiments;
- current bottlenecks;
- current health-monitoring state;
- current compound-learning state;
- current executable findings;
- current predictive/metacognitive posture;
- immediate next actions.

## Layer 2 — DURABLE DOCTRINE
Things that remain valid across individual experiments.

Contains:
- identity/topology principles;
- TSIT;
- SLR / Context Arc;
- environment-vs-substrate deconfounding;
- health-monitoring doctrine;
- finding maturity;
- compound-learning gates;
- executable finding rules;
- predictive-metacognitive loop;
- protected-strength doctrine;
- reinvestment / return-on-learning doctrine.

## Layer 3 — SOURCE HISTORY / PROVENANCE
Why the doctrine exists.

Contains:
- retired Substrate Lab lineage;
- BHL 1.2 lineage;
- Phase-1 Hourly natural-history cohort;
- W1/W2/W3;
- A/B/C durability work;
- PR/Issue registry;
- superseded hypotheses;
- negative results;
- historical corrections;
- transcript reconciliation status.

This prevents history from being mistaken for Current while preserving reconstructability.

# 5. VERSIONING MODEL

Every new Master Spine version should include:

## Version header
- version;
- date;
- successor thread / compiler;
- source predecessor version;
- status;
- authority boundary.

## Delta block
- ADDED
- CHANGED
- SUPERSEDED
- REMOVED FROM CURRENT
- STILL OPEN

## Current-state checkpoint
A concise machine/human-readable summary of present state.

## Source lineage
Exact prior artifacts relied upon.

The next version must never silently rewrite the prior version.

---

# 6. END-OF-THREAD SUCCESSION PACKET

Before a BHL thread is retired, it should produce a **BHL Succession Packet** with:

### A. Current state
- current Master Spine version;
- current Binding Ledger;
- current Findings Ledger;
- current Experiment Registry;
- current Cohort/Context-Arc Index;
- current Population Health Board;
- current monitoring/throughput controls;
- current Executable Findings catalog.

### B. Work in progress
For each open item:
- owner;
- state;
- last completed step;
- unresolved blocker;
- evidence already gathered;
- next justified step.

### C. Current bottlenecks
- primary bottleneck;
- secondary bottleneck;
- queue aging / starvation;
- identity gaps;
- evidence gaps.

### D. Important negative instructions
- what not to infer;
- what not to restart blindly;
- stale/superseded state to avoid;
- unresolved authority boundaries.

### E. Source links
- exact file names / versions;
- PRs / issues;
- relevant transcripts;
- source-native evidence references.

### F. Successor startup sequence
1. load Current section;
2. verify latest sourcebook version;
3. inspect delta from predecessor;
4. inspect open WIP;
5. verify material live state if needed;
6. resume only from the smallest justified next step.

---

# 7. START-OF-THREAD SUCCESSION PROTOCOL

The successor BHL thread should:

1. declare itself successor;
2. load the latest Master Spine;
3. load the latest Succession Packet;
4. distinguish:
   - CURRENT
   - CANDIDATE
   - HISTORICAL
   - SUPERSEDED
   - UNKNOWN
5. verify any material external/live state;
6. state reconstructed Current;
7. state unresolved gaps;
8. continue from current work queue.

No successor should treat old conversational memory as governing truth when the Sourcebook says otherwise.

# 9. SOURCE HISTORY RULES

Institutional source history should preserve:

- original observations;
- later reinterpretations;
- superseded interpretations;
- negative findings;
- failed experiments;
- apparatus confounds;
- identity corrections;
- temporal corrections;
- why a doctrine changed;
- when the doctrine changed;
- what evidence caused the change.

Historical truth and Current truth must be separately queryable.

---

# 10. ANTI-CONTEXT-GRAVITY DESIGN

The Sourcebook must actively prevent stale-state resurrection.

Every historical item should carry, where applicable:
- status;
- validity window;
- supersession relation;
- current-truth relation;
- evidence maturity;
- authority status.

A historical artifact is provenance, not automatic Current.

---

# 11. INSTITUTIONAL KNOWLEDGE STANDARD

A BHL lesson becomes durable institutional knowledge only when it is increasingly:

- evidence-supported;
- provenance-linked;
- status-bounded;
- temporally situated;
- retrievable;
- transferable across substrates;
- reusable;
- falsifiable;
- linked to counterexamples;
- connected to operational or research consequence.

Stored text alone is not institutional knowledge.

---

# 12. SUCCESSION QUALITY METRICS

Measure whether the Sourcebook itself works.

Possible measures:
- successor time-to-correct-current-state;
- number of stale-state errors after succession;
- Founder reconstruction burden;
- missing-source rate;
- duplicated research rate;
- repeated experiment rate;
- unresolved identity rework;
- time from successor start to productive BHL work;
- percentage of prior open WIP correctly resumed;
- percentage of superseded material incorrectly revived.

This makes continuity itself a BHL research object.

---

# 13. SOURCEBOOK METACOGNITION

After every major succession, ask:

- What did the successor misunderstand?
- Which sections were hard to reconstruct?
- What information was missing?
- What information was excessive?
- Which historical material created context gravity?
- Which compact representation restored Current fastest?
- What should the next Sourcebook version change?

The Sourcebook should become better at creating future successors.
